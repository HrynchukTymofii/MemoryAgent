Technical Architecture — Revision A

Personal Memory OS

A local-first desktop assistant for capturing, organizing, retrieving and acting on personal knowledge through a global voice shortcut. This document records the architecture, the reasoning behind each decision, and where it deliberately departs from the original specification.

StatusApproved for build
Date6 September 2026
Supersedespersonal_memory_os_spec.md
PlatformWindows first, macOS next
Local — runs on the user's machine, never fails Cloud — runs on AWS, can be smarter

01 Summary

What we are building and why it is shaped this way

The product is a control layer between the user and their computer. Press a shortcut, speak, and the system understands the context, performs the action, and disappears. The engineering problem is not intelligence. It is friction.

Everything in this document descends from one number: the user must see a result within roughly one second of finishing speaking. That budget is what makes the product a habit rather than an app. If capture is slower or less reliable than the user's existing bad habit — leaving a browser tab open — the product loses, regardless of how good its retrieval is.

The architecture is therefore split by a single rule. Anything on the capture path runs locally and cannot fail. Anything on the retrieval or reasoning path may cross the network and should be as smart as we can afford. This split is not a compromise between local and cloud; it is a division by physics, and it happens to place the interesting engineering work in the cloud tier where it belongs.

Capture is a reflex. Retrieval is a query.

Reflexes must be local. Queries can afford the network.

The four decisions that define the system

DecisionChoiceBecause
Client storeSQLite + FTS5 + sqlite-vec A capture must succeed offline, instantly, always. Postgres on a customer machine is an installer, a service and a support ticket.

Model routingThree tiers: grammar, small local LLM, cloud Most commands are formulaic and deserve no inference at all. Hard commands deserve a real model.
Cloud roleAuthoritative store, reranking, agents Quality work that is not latency-critical: cross-encoder reranking, research, planning, sync.

02 The organizing principle

Why the capture path never touches the network

There are two distinct moments in this product, and they have opposite requirements.

The reflex. The user is mid-thought. They hit the shortcut and speak without breaking their attention. They are not waiting for the system; they are using it the way they use a keyboard. Any hitch breaks the flow, and any failure is data loss — the thought is gone.

The query. The user has stopped what they were doing and asked a question. They are prepared to wait. Four hundred milliseconds is invisible; being right matters far more than being instant.

Average latency is the wrong metric

The tempting comparison is that local capture takes about 250 ms and cloud capture about 350 ms, so cloud is fine. That comparison is misleading, because for a tool pressed forty times a day the user does not perceive the median — they perceive the worst case.

ConditionLocalCloud (warm socket, regional)
P50, good connection250 ms300–400 ms
P95300 ms700 ms
P99350 ms2–4 s
Hotel wi-fi, train, VPN350 ms3 s or fails
Offline350 msfails

The first row is a tie. The last three rows are the entire product. A capture tool that works ninety-eight percent of the time is not ninety-eight percent as good as one that works every time — it is substantially worse, because the user stops trusting it and reverts to the old habit. Trust is lost at the second failure, not the fiftieth.

Both at once — but never wait for a timeout

Reflex and query are not two modes the system switches between. They are two kinds of moment: saving is always a reflex, searching is always a query. The question that matters is a different one — when the cloud could help, how do we use it without ever being hurt by it?

The obvious answer is a fallback chain: try the cloud, and if it fails, use local. That is a trap, and it makes the worst case worse. A chain has to wait for the cloud to fail before the local path can begin, so a two-second timeout plus 300 ms of local work is 2.3 seconds. An occasional failure has been converted into a guaranteed slow path.

Race, don't chain. Both start at the same instant.

The local result is always what is shown. The cloud only ever upgrades what is already on screen.

PathLocalCloudWhat the user experiences
Transcript Always runs; drives the overlay and the router Re-transcribes the same audio asynchronously Sees local text immediately; the stored text is silently upgraded later
Intent routing Always decides the action Not used on the capture path at all Never waits on a network call to save something
Search ranking Always runs, ~40 ms Reranks, with a 400 ms budget Local list appears at once; order improves in place if the rerank arrives in time
Research, plan, explain Not possible locally Required An honest "needs a connection" — never a spinner that ends in an error

The invariant is simple enough to hold in your head while writing any feature: nothing the user is looking at ever waits for a network call to fail. Cloud work is either already overlapping something local, or it is an enhancement that swaps in when it arrives, or it is a capability that is honestly reported as unavailable. It is never a dependency in the middle of a path the user is waiting on.

A useful side effect: this makes the offline case require no special code. There is no "offline mode" to build and no branch to test — offline is simply the case where the enhancement never arrives, and the system was already designed to render correctly before it did.

03 System overview

Components, and which side of the boundary they live on

The client is a single Tauri 2 process. There is no Python sidecar, no localhost HTTP server, and no inter-process serialization anywhere on the capture path — a capture is a direct function call from the hotkey handler to SQLite. The cloud tier is a conventional FastAPI service on AWS that the client talks to asynchronously and can always survive without.

Crate dependency direction

Acyclic, with memos-core at the root holding domain types and no I/O. Only memos-context needs a platform-specific implementation, and it already hides that behind a trait — which is what will make the macOS port cheap.

  ├── memos-db        SQLite, migrations, repositories
  ├── memos-embed     EmbeddingProvider trait + ONNX implementation

04 The latency budget

A contract, not an aspiration

Each stage below has an owner and a ceiling. If a change pushes any stage over its ceiling, the change is wrong. The total from key release to visible acknowledgement is under 700 ms in the worst tier-1 case and under 350 ms when the fast path matches.

Stage 1 — measured, not projected

Built and instrumented in M0. On a Ryzen 7 7800X3D, debug build with the dev server still in the path, hotkey → overlay painted measured 9.9 ms median and 15.8 ms at p95 against the 50 ms ceiling — roughly five times the headroom the budget needs. Synthetic injection over ten cycles reproduced the same distribution, so it is a stable figure rather than a lucky run.

The number holds for one reason: the overlay window is constructed and painted at startup and merely shown on the shortcut. The native position-and-show call itself costs 0.4 ms; the remaining ~9 ms is IPC and compositing. Building the window on demand would cost 200–400 ms and blow the budget on its own.

The mistake almost everyone makes

Stage 2 is where this class of product usually breaks. Opening a WASAPI capture device costs 100–300 ms. If that happens when the hotkey is pressed, the first word is clipped and the product feels broken in a way users cannot articulate but immediately dislike. The microphone stream is opened at application start and never closed. The hotkey does not open a device; it records a read offset in a ring buffer that is already full of audio.

05 Capture pipeline

From key press to a durable row

Audio

A cpal stream on the WASAPI backend writes 16 kHz mono samples continuously into a fixed-size ring buffer holding the last 30 seconds. Voice activity detection runs on the live stream so the system knows where speech begins and ends without waiting for the key.

Because the buffer already contains recent audio, one genuinely useful feature comes free: retroactive capture. The user can press the shortcut immediately after saying something aloud and the system can still transcribe it.

Transcription

whisper.cpp transcribes rolling windows while the user is still speaking, so partial text appears in the overlay within a few hundred milliseconds of the first word. Model size is chosen by hardware tier. A dual-path arrangement gives us local speed and cloud accuracy at once:

  • Local, synchronous. Drives the overlay and the intent router. Never blocks.
  • Cloud, asynchronous. The same audio is re-transcribed by a larger model in the background and the stored text is upgraded in place. The user has already moved on.

Local transcription also gets a capability that cloud APIs largely deny us: decoder biasing. Whisper accepts an initial prompt, into which we inject the user's real collection names, tags and recently seen entities. So “put this in Flari” transcribes as Flari, not flurry. Proper nouns are simultaneously the tokens the intent router most depends on and the ones a generic model most often gets wrong.

Context acquisition

Running in parallel with the speech, not after it, so it costs nothing on the timeline.

{
  "active_application": "Chrome",
  "active_window_title": "React — State as a Snapshot",
  "current_url":        "https://react.dev/learn/state-as-a-snapshot",
  "selected_text":      "State is a snapshot for each render...",
  "clipboard_text":     null,
  "selected_files":     [],
  "captured_at":        "2026-09-06T20:14:03+03:00"
}

On Windows this uses GetForegroundWindow for the application and title, and UI Automation for selected text and the browser URL. Every field is permission-gated and individually disableable in Settings, and the whole object is shown to the user on demand — provenance is a trust feature, not a debug feature.

Memory footprint

Resident memory is the RAM the application holds while sitting idle in the tray, doing nothing. It is not zero, and the reason is the latency budget: loading a whisper model from disk takes 300–800 ms, so if models load on demand, every single capture pays that cost. The models have to already be in memory for the numbers in section 4 to hold.

The question is how much. An earlier draft of this document quoted roughly 1 GB and presented it as the default. That was the worst case, not the default, and it was wrong to present it that way — the real default is about a third of it.

The local LLM was the entire problem, and accounts are what let us drop it. This is a multi-user product with sign-in and a metered plan, so users are online essentially all the time. Tier 1 routing can therefore run in the cloud for most people, and the local router becomes an optional download for those who want full offline operation — not something every user carries in RAM forever.

Loading policy — speculative, not lazy

The obvious next question is why anything is preloaded at all. Only the hotkey and the speech need to be instantaneous; routing and storing a memory can afford a second. So why not load models on demand and keep idle memory near zero?

Because plain lazy loading does not remove the cost, it relocates it — onto the first command after launch, which is precisely the command where the user forms their impression of the product. Waiting two seconds every morning is worse than it sounds.

There is a better option, and it comes from the same observation that made section 4 work: the user's speech is two to four seconds of free time. So models are not loaded when they are needed. They are loaded on hotkey-down, in parallel with the user speaking — and by the time the transcript is final, they are warm.

ComponentSizeLoadedRationale

Embedding model35 MBBackground worker, only when it has queued workAlready off the critical path; unloaded again when the queue drains

Two supporting mechanisms make this cheap:

  • Memory-map rather than read. llama.cpp mmaps model weights, so pages are file-backed and demand-paged. The OS can reclaim them under pressure, and "loading" is mostly address-space bookkeeping rather than I/O.
  • Unload on idle. After roughly five minutes of inactivity the router is dropped and the process returns to its idle floor. A speculative reload costs nothing visible.

Idle memory is roughly 310 MB, and the 400 MB router is only resident for the few seconds around a command that actually uses it — and only at all for users who choose local routing. The default sends routing to the server, exactly as you suggested, which makes the local model a genuine option rather than a tax everyone pays.

06 Model architecture

Three tiers, chosen by how much thinking a command actually needs

The original specification defined a provider interface but never said which model runs when. Without that policy the natural failure is calling one general-purpose model for everything, which makes trivial commands slow and hard commands unreliable. Routing is by difficulty, not by capability.

Tier 0 — deterministic, no model

Real voice commands are overwhelmingly formulaic. A hand-written grammar covers the common shapes and resolves them against the live collection list:

save this to <collection>        tag this <tag>
remind me <temporal>             open <ref>
find <query>                     move this to <collection>

Spending 400 ms of GPU time on “save this to React” is waste. Tier 0 is the single largest latency win available, it is deterministic and unit-testable, and it costs nothing per call. Its hit rate is a product metric: if it falls below about 40 %, either users phrase things differently than assumed or the grammar needs extending, and the correction log will say which.

Tier 1 — the local router

A sub-2B parameter instruct model via llama.cpp, emitting a small JSON object. Two properties are load-bearing and neither is optional:

Grammar-constrained decoding. A GBNF grammar is regenerated whenever the collection set changes and enumerates the valid intents and the user's actual collection paths as literal alternatives. The model therefore cannot emit malformed JSON, an unknown intent, or a collection that does not exist. This is what makes a sub-billion-parameter model safe to trust — the guarantee is structural, not a matter of prompt wording.

A warm, reused KV cache. The system prompt plus collection list runs to about 800 tokens. Re-prefilling that on every command costs over 100 ms; caching the prefix costs effectively nothing. The model loads once at startup and stays resident for the process lifetime.

{ "intent": "SAVE",
  "slots":  { "collection": "Study/Programming/React",
              "title": "State as a Snapshot",
              "source": "https://react.dev/learn/state-as-a-snapshot" } }

Tier 2 — cloud reasoning

Claude or GPT behind the same LlmProvider trait, orchestrated by LangGraph. Handles research, planning, explanation, quiz generation, and any disambiguation the router could not settle. The user has switched mental mode by this point, so a two-second response is entirely acceptable — and this is where the metered free tier applies.

Embeddings

bge-small-en-v1.5, 384 dimensions, through ONNX Runtime rather than PyTorch: roughly 30 MB instead of 800 MB, and 5–15 ms per short text on CPU. Always off the critical path — a save is acknowledged before its embedding exists, and a background worker backfills. Cloud re-embedding with a larger model runs on sync for paid users.

07 Retrieval

Hybrid by default, reranked when it matters

The system is not a vector database with a chat interface. Vector similarity is one signal among several, and on its own it is notably bad at exact terms — product names, acronyms, URLs, people. Keyword search is bad at meaning. The combination beats either alone, and a cross-encoder reranker beats the combination.

Why the reranker is worth a network hop

Vector search encodes the query and the document separately, so it can only compare two summaries. A cross-encoder reads the query and each candidate together and scores the actual relationship between them. It is far too slow to run over a whole corpus, which is exactly why it belongs at the end of a pipeline that has already narrowed to fifty candidates — and far too slow to run locally, which is why it belongs in the cloud.

This is the single component that most improves the moment users care most about: “find that thing I half-remember.” It is also not latency-critical, so it costs the product nothing where the product is fragile.

Ranking signals

score = w1·semantic_similarity      // sqlite-vec cosine
      + w2·keyword_score           // FTS5 BM25
      + w3·recency_decay           // exponential, half-life ~30 days
      + w4·collection_match        // query mentions or implies a collection
      + w5·source_match            // domain, file type, capture method
      + w6·relationship_distance   // graph hops from an anchor item
      + w7·access_frequency        // items reopened are items that matter

Weights start hand-set and are later tuned against the correction log, which records which result the user actually opened — a genuine relevance label collected for free.

08 Confidence and undo

No unnecessary questions, no dangerous guesses

The original specification shows the model emitting its own confidence numbers. That is the one part of it I would reject outright. Self-reported LLM confidence is badly calibrated — models produce round, confident-sounding numbers largely independent of whether they are correct, and a quantized sub-billion-parameter router is the worst case for this. Gating actions on a number the model invented gives the appearance of a safety system with none of the substance.

There is a subtler failure the specification's own example exposes:

"Put this with the house stuff."
    House / Internet      0.51
    House / Electricity   0.49

Neither score is low. What makes this ambiguous is not the absolute score but that the top two are indistinguishable. A threshold on the top score alone would miss this case entirely, while needlessly interrupting a confident lone match at 0.55 that has no competitor.

Confidence is computed by us, from measurable signals

confidence = f(
    slot_token_logprobs,      // from the constrained decode, per slot
    retrieval_margin,         // score(top-1) − score(top-2)   ← the important one
    historical_accept_rate    // this intent, this user, from the correction log
)
  • Per slot, not per command. The intent can be certain while the destination is not. Only the uncertain slot is queried, so the question stays narrow — “Internet or Electricity?” rather than “what did you mean?”
  • Margin drives destination choices. Low margin means ask, whatever the absolute score.
  • Thresholds are calibrated from logged outcomes, per intent, not hand-tuned global constants. TAG should act freely; FILE_OPERATION should not.
Two rules that override everything

1. Irreversible actions always confirm, at any confidence. Deleting or overwriting files is never executed automatically.

2. Everything else is undoable. Every executed command writes an inverse operation and the confirmation carries an undo affordance. Cheap undo is what allows the thresholds to be aggressive, and aggressive thresholds are what keep the product fast. The two are the same design decision viewed from different ends.

Structured first, embeddings second

Provenance is a product feature

Every item keeps where it came from, when, and by what method — highlighted text plus voice command, a dropped file, a research result the user approved. This is what lets the user reopen the original source and, more importantly, what makes them trust that the system has not silently invented or misfiled something.

10 Cloud tier

Where quality work happens, on AWS

The cloud tier is a conventional, well-understood service stack. Its defining property is that nothing in it is required for the client to function — every capability degrades to a local equivalent or is simply absent until the connection returns.

Why LangGraph lives here and not on the client

LangGraph's real strengths are durable state, branching, retries and human-in-the-loop interrupts. None of those are what a SAVE command needs — a save is classify, resolve, write a row. Putting a Python graph runtime on the capture path would buy nothing and cost a bundled interpreter, a multi-second cold start and cross-process serialization on every command.

Put it where multi-step work actually happens and it earns its keep immediately. The research agent alone — search, fetch, extract, rank, present, await user selection, save the approved subset — is a genuine graph with a human interrupt in the middle, which is precisely the shape LangGraph exists for.

11 Sync

Write-ahead locally, reconcile in the background

The non-negotiable property: a capture never blocks on the network and never fails because of it. Writes land in SQLite and in an outbox table within the same transaction. A background worker drains the outbox whenever a connection exists. If the machine is offline for a week, nothing is lost and nothing is felt.

Conflict resolution is field-level last-write-wins with the full history retained in the events table, so a losing edit is recoverable rather than destroyed. Items are append-mostly in practice, which keeps genuine conflicts rare.

12 Identity and security

Multi-user from day one, server-readable, stated plainly

An earlier draft of this document omitted accounts entirely, which was a straightforward gap: this is a multi-user product with a metered plan, so identity is not an optional extra bolted on at billing time. It determines the data model, the sync design, the metering, and what the first screen of the application is.

Authentication

Three sign-in methods, all landing on the same account record:

MethodMechanismNotes
GoogleOAuth 2.0 + PKCE, system browserExpected default for most users. No password to lose
AppleSign in with Apple, OIDCRequired once the macOS/iOS build ships if any other social sign-in is offered — App Store policy
EmailMagic link, or password + verificationMagic link preferred: no password storage, no reset flow, fewer support tickets

OAuth runs in the system browser, never in an embedded webview. Google blocks embedded-webview OAuth outright, and it is the correct security posture regardless: the desktop app opens the default browser, receives the callback on a loopback listener, and exchanges the code with PKCE. The app never sees the user's credentials.

desktop app
  → opens system browser to the provider
  → user authenticates with Google / Apple / email
  → provider redirects to http://127.0.0.1:<ephemeral>/callback
  → app exchanges code + PKCE verifier at our API
  → receives access token (short-lived) + refresh token (device-bound)
  → refresh token stored in Windows Credential Manager, never in SQLite

The token model

Access tokens are short-lived and refreshed silently. The refresh token is bound to the device record created at activation, so revoking a device from Settings genuinely revokes it. Crucially, an expired token does not stop the application from working — it degrades exactly the way the entitlement grace period does in section 16. A user whose token could not refresh because they were on a plane still captures, still searches, still opens their own data.

A consistency fix this forces

An earlier draft claimed the free tier required no account. That cannot be true once the free tier is metered — a usage counter needs an identity to attach to. An account is required for everyone.

What survives is the thing that actually mattered: a Local-only processing setting, where the account exists for identity and billing but content is never synced and never leaves the machine. That is a privacy guarantee about data, which is what users care about — not about whether they had to sign in once.

Multi-tenancy

Every row in the cloud Postgres carries a user_id and is protected by row-level security, so tenant isolation is enforced by the database rather than by remembering to add a WHERE clause. The local SQLite file is single-user by construction — it lives in the user's own profile directory and is encrypted with a key held in Windows DPAPI, bound to their Windows account. Two people sharing a PC get two separate databases without any application logic.

Onboarding

The first run has to accomplish four things without feeling like a setup wizard, because the product's whole promise is low friction and the first ninety seconds either prove that or refute it:

  1. Sign in — one tap for Google or Apple.
  2. Microphone permission — with the always-open stream explained honestly, in one sentence, before it is requested.
  3. Choose the shortcut — a default is proposed and can be changed later.
  4. First capture — guided, ending in something actually saved. The user should have used the product before onboarding is over, not merely configured it.

The chosen data model

Server-readable encryption. Data is encrypted in transit and at rest, but the service can decrypt it in order to embed, rerank and reason over it. This is the standard SaaS posture and it is what makes the cloud tier useful at all.

The alternative — end-to-end encryption with client-held keys — was considered and rejected for this version, because it is close to incompatible with cloud retrieval. If the server cannot read plaintext it cannot embed, cannot rerank, and cannot feed a reasoning model. The cloud tier would collapse into an encrypted blob store, taking most of the product's quality advantage with it. That trade may be worth revisiting later as a premium "private vault" mode.

The obligation this creates

Choosing server-readable means the privacy claim must be accurate and prominent, never buried. Users are told, in plain language and before they enable sync, that synced content can be read by the service in order to provide search and reasoning. A product built on trust cannot afford a privacy page that overstates.

  • Raw audio. Discarded after transcription unless the user explicitly enables cloud STT, and even then it is sent for transcription and not retained.
  • Clipboard contents and screenshots that were not part of an explicit save.
  • The correction log, by default. It is a record of what the user said and did. Syncing it is opt-in, and it must be exportable and deletable from Settings.
  • Anything at all, in Local-only processing mode — a first-class setting, not a degraded state. The account still exists for identity and billing, but no content is ever synced or sent for cloud enrichment. Capture, search and organization are unaffected.
The always-open microphone

Section 5 keeps an audio stream open permanently. This is a real privacy surface and must be communicated honestly: a persistent tray indicator whenever the stream is live, a hard mute control, and a plain guarantee that buffered audio is discarded continuously and never written to disk unless the user presses the shortcut. Getting this wrong is not a bug, it is a trust catastrophe — so it is stated in the interface, not only in a policy document.

13 Interface

The overlay is the product; the hub is where everything else lives

Roughly ninety percent of interactions happen in a small overlay that appears for two seconds and disappears. The main window — the Hub — exists for browsing, correcting, reviewing and configuring. Designing the Hub first would be designing the wrong product, but omitting it, as an earlier draft of this document did, leaves the application without a shape.

Visual direction

Two references, taken deliberately rather than reinvented, and each contributing a different layer:

  • Wispr Flow supplies the structure. A left navigation rail with a usage meter pinned to its base, a single large content panel, a right rail for figures, and a two-column settings layout. Serif for headings and numerals against a geometric sans for interface text.
  • Polaris supplies the palette. A cool blue-grey ground with pure white panels, near-black cool ink, generous radii and soft diffuse shadows.

Two details from Polaris are worth naming because they do real work:

Selection is elevation, not colour. The active navigation item is a white pill lifted off the blue-grey rail with a soft shadow — no accent fill, no coloured text. This keeps the entire chrome monochrome, which means the few places we do use colour carry actual meaning rather than competing with decoration.

Icons have dimension. Soft gradient tiles with an inner highlight rather than flat monochrome glyphs. It is a small thing that separates a considered interface from a templated one, and it costs nothing at runtime.

15 Personalization

The correction log is the asset; LoRA is deferred

The specification proposes fine-tuning a small model on the user's own command history. The direction is right; the sequencing is not. LoRA needs thousands of examples to beat a good prompt, and a new user has none. Worse, retraining is a batch job — so a correction made today would not change behaviour until the next training run, and a system that repeats a mistake it was just corrected on reads as broken.

Phase 1 — nearest-neighbour few-shot, ships in V1

Embed the incoming transcript, retrieve the most similar past commands together with their corrected outcomes, and inject them as examples in the router prompt.

  • Works from roughly the tenth example.
  • A correction takes effect on the very next command, with no training step.
  • Fully inspectable — “I filed it there because you filed a similar thing there last Tuesday” is an explanation. Weights are not.

Phase 2 — LoRA, later and on evidence

Once the log holds thousands of corrections and Phase 1 is demonstrably the bottleneck, train an adapter in the cloud tier and ship it as a per-user artefact. The log schema is designed now precisely so this needs no migration.

The same log does quadruple duty: it is the evaluation set for router changes, the calibration data for the confidence thresholds in section 8, the coverage metric for the Tier 0 grammar, and the relevance labels for tuning retrieval weights in section 7. It is the most valuable table in the system, and it costs nothing to collect.

16 Business model

Meter what costs money, give away what does not

The meter counts voice inputs. One press of the shortcut, one thing spoken, one action performed — that is one capture, whatever it turned into. Fifty per week free, then the user upgrades.

The one line that must not be crossed

Running out of captures must never restrict access to memories the user has already saved. Browsing, searching, opening and exporting stay unlimited on the free plan forever. The meter gates new capture, not the archive. A product that locks people out of their own notes to extract a payment has stopped being a memory system.

Two consequences worth designing for now

The counter has to work offline. Capture is local and must succeed without a network, so the count is incremented locally and reconciled on sync. This permits a small amount of over-run if someone is offline for a long stretch — which is the correct way to be wrong. The alternative, refusing to capture because the server is unreachable, would break the product's central promise to protect a few cents of revenue.

The reset window matters as much as the number. Fifty per month is roughly seven a week, which a moderately active user exhausts in two days and then spends twenty-eight days locked out. That is long enough for the habit to die, and a dead habit does not convert — it uninstalls. Fifty per week is about seven a day, and more importantly the wall is never more than a few days from lifting, so the behaviour survives the gap.

This is why the reference product also resets weekly rather than monthly. The allowance is a throttle on heavy use, not a cliff.

Fifty is still a hypothesis. A capture is roughly a thought, and a genuinely heavy user may produce fifteen a day. Wispr Flow meters words per week instead, which scales with intensity rather than counting events — defensible, and harder to explain. Ours is simpler: the counter reads 32 of 50 captures and needs no footnote. Instrument the real distribution from the first week of use and treat the number as tunable; the reset cadence is the part worth keeping fixed.

Payments

Stripe does not offer merchant accounts to Ukrainian entities, so Paddle is the chosen merchant of record: it is the legal seller, so it handles EU VAT, sales tax and invoicing across every jurisdiction, and it is the most established option of the group — a long track record with desktop software specifically, mature subscription handling, and proper dunning for failed renewals. Polar and Creem are the newer alternatives; Lemon Squeezy inherits the original problem now that it is Stripe-owned.

The one thing Paddle does not provide is licensing. Polar ships license keys and entitlement checks as first-class primitives; Paddle leaves that to the integrator. In practice this costs little here, because the offline entitlement design below is something we would build regardless — Paddle handles the transaction and the subscription state, and memos-license owns key issuance, device activation and offline verification. It is worth knowing the boundary sits there rather than discovering it during M4.

Open items — must be resolved before launch

Payout eligibility. Support for a specific Ukrainian entity has not been confirmed with Paddle. Verify directly before building M4.

Onboarding review. Paddle vets sellers before approving an account, and review can be slow and occasionally strict for new AI products. Start the application early — it is a lead-time risk, not a technical one.

Both are why the integration sits behind a BillingProvider trait: swapping to Polar or Creem must be a one-file change, not a refactor.

Licensing must not break the local-first promise

purchase (Paddle)                 ← Paddle owns the transaction
   → webhook to our API           ← and the subscription state
   → license key issued by us     ← memos-license owns everything below
   → device activation, N seats
   → signed entitlement token (Ed25519, short-lived)
   → cached locally, verified offline against an embedded public key
   → refreshed opportunistically · ~14-day offline grace period

The client holds only a public key, so no network call is needed to validate an unexpired token. After the grace period an expired entitlement degrades rather than bricks: Pro features switch off, and the user retains full access to everything they have already captured. Holding a user's own memory hostage would be both wrong and the fastest possible route to a chargeback.

17 Changes from the original specification

What changed, and the reasoning in each case

The original document is strong on product. Principle 5 (“fast before clever”), Principle 6 (“structured data first, RAG second”) and the confidence system are the three ideas that most shape what is built here, and they survive intact. The changes below are all in the technical layer, and most of them come from one observation: the specification's stack was written for a server, and the product is a desktop application sold to strangers.

SectionSpecification saidNowReasoning
13Postgres + pgvector as the client's primary database SQLite + FTS5 + sqlite-vec on the client; Postgres authoritative in the cloud An installer, a Windows service, a port and a migration on every update — before the user has seen the product work. Also genuinely faster: hybrid search becomes one in-process SQL query.
14Redis on the client SQLite jobs table, Tokio tasks, Tauri events; Redis in the cloud No official Redis build for Windows. All three of its client-side roles have in-process equivalents.
15LangGraph in the main command flow Rust state machine on the capture path; LangGraph for Tier 2 in the cloud A save is “classify, resolve, write a row” — not a workflow graph. A bundled Python runtime would cost a multi-second cold start and per-command serialization for no benefit.
17Model reports its own confidence Confidence derived from logprobs, retrieval margin and history Self-reported confidence is badly calibrated. The specification's own “house stuff” example is a margin problem that a top-score threshold would miss.
18whisper.cpp, local Kept, plus an always-open ring buffer and asynchronous cloud re-transcription Opening the audio device on hotkey press costs 100–300 ms and clips the first word. Dual-path gives local speed and cloud accuracy in the same interaction.
19Fish Speech for local TTS Dropped. OS built-in TTS behind a trait; cloud TTS optional later Not because it is too large — it is about 0.5B parameters and runs fine — but because it drags PyTorch into a Rust app, and because speaking a response makes the interaction longer in a product whose promise is that the overlay disappears.
20Provider interface, model unspecified Three explicit tiers with a routing policy A provider interface without a routing policy leads to calling one model for everything, which is slow for easy commands and unreliable for hard ones.
21LoRA as the personalization plan Correction log and kNN few-shot first; LoRA on evidence LoRA needs thousands of examples; new users have none, and batch retraining cannot deliver the immediate correction feedback users expect.
11Hybrid retrieval — keyword, semantic, metadata Kept, plus a cloud cross-encoder reranking stage The largest available quality gain for “find that thing I half-remember,” and it is not latency-critical, so it costs nothing where the product is fragile.
33Everything local, cloud optional Capture strictly local; retrieval and reasoning cloud-enhanced The split now follows the failure consequence: a failed capture loses a thought, a failed query loses 400 ms.
What did not change

All eight product principles. The command taxonomy in section 6. The knowledge model and its graph structure. Provenance. Hybrid retrieval. The staged product evolution. The decision to keep the learning layer out of V1. These are the parts of the original document that were right, and they are the parts that determine whether the product succeeds.
